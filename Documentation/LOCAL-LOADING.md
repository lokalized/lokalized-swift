# Local catalog loading

`LocalizedStringLoader.parse(InputStream, locale:source:warningHandler:loadingOptions:)` reads strict UTF-8 from the current stream position. It opens a stream whose status is `notOpen` and never closes a supplied stream, including after failure. The caller owns its lifecycle. A zero-byte Foundation stream read means EOF; asynchronous streams that temporarily have no bytes must be consumed by their owner before calling this synchronous API. Locale validation precedes opening the stream. The existing `Data` and `String` parsing APIs retain their original validation order.

`parse(file:locale:...)` follows symbolic links, records the canonical path in origins and warnings, and always closes its owned descriptor. A canonical path containing invalid UTF-8 is refused before opening; the loader never repairs it into a different filename. Reads use chunks of at most 8 KiB and stop after at most `maximumInputBytes + 1` bytes. The extra byte detects overflow. The aggregate byte limit is charged before the per-resource byte refusal. Byte inputs do not incur the String API's UTF-16 character limit.

`loadFromDirectory(URL,...)` scans immediate entries without recursion. Actual entries, including hidden files, ignored names, and subdirectories, count toward discovery. Literal leading-dot filenames are ignored. Directories are skipped before filename recognition, including symlinked directories and directories ending in `.json`. Recognized files have a known locale tag as their complete name or as the stem before one ASCII case-insensitive `.json` suffix. Unknown extensionless names and other extensions are ignored; an invalid `.json` stem is an error. Locale recognition uses the pinned JDK/CLDR implementation, independent of the host's locale data. Suffix recognition uses UTF-8 bytes, including beside combining or Unicode Prepend characters.

Discovery completes within its configured limit before any catalog is parsed or warning delivered. At most that many names are retained; the next entry is refused before retention. Names are then processed in lexicographic UTF-8 byte order. This bounded ordering is a native adaptation: Java's filesystem enumeration order can produce a different first error or warning when several entries are faulty. In particular, `notes.json` precedes `zz.json` here. Discovery overflow wins over a fault or warning in a selected file. Invalid UTF-8 filenames are never repaired into recognized locale stems: invalid `.json` candidates are refused, while unrecognized extensionless names are ignored. A refusal's display name may contain the replacement character; actual-entry directory classification uses the original bytes.

An equal typed locale key is refused before opening its second selected file. Distinct Java-compatible locale identities that render the same tag are refused after the selected files have parsed. For example, the legacy `no-NO-x-lvariant-NY` identity and `nn-NO` both render `nn-NO`. Explicit `loadFromResources([LocaleTag: URL],...)` mappings validate their complete count, locale keys, URL paths, and exact rendered-tag collisions before opening any mapped resource; arbitrary filenames are allowed. Both loaders check case-insensitive rendered-tag collisions after parsing. Thus distinct variant identities `en-ABCDE` and `en-abcde` can deliver warnings or encounter a parsing failure before that final collision check. Mappings are processed by rendered tag, with underlying Java locale identifier as a tie breaker. Returned Swift dictionaries do not promise iteration order.

Every directory or explicit-mapping call shares input-byte, localized-file, translation-node, warning, and discovery counters. JSON depth and individual resource byte limits remain per resource. Returned `ParsedStringsFile` values contain only their own warnings and origins. A warning is counted before its handler is invoked; a warning beyond the shared limit is not delivered. A thrown warning-handler error propagates unchanged, and handlers may reenter loaders because each load owns its counters.

Selected resources must be local file URLs and regular files. Canonicalization and mode checks follow symlinks and refuse dangling links, FIFOs, sockets, devices, and directories before opening. Nonblocking open followed by `fstat` also refuses a special-file replacement between the initial check and open. Content changes to a regular file are bounded by actual reads; the loader does not promise a filesystem snapshot or sandbox files to a particular directory. Only the file mode is consulted from `fstatat`/`fstat`; no timestamps, sizes, or inode values are read, persisted, or transmitted. The packaged privacy manifest covers metadata APIs used only when the caller explicitly loads local resources. It is an SDK declaration, not certification of an application's privacy submission.

`LocalizedStringLoadingError` identifies transport, discovery, invalid-resource, and duplicate-locale failures and retains an immediate native I/O cause where available. Catalog UTF-8, JSON, schema, and resource-limit failures remain `StringsParseError`. Locale validation produces `LocaleTagError`. Application warning-handler errors retain their identity and are not wrapped as I/O errors.

The portable library has no external dependencies. Bundle wrappers resolve only caller-selected bundle paths and delegate to these loaders; they do not apply `.lproj` negotiation or implicit process-bundle discovery. Java classloader/JAR scanning and JavaScript asynchronous manifests, authentication, caching, and transport services are separate platform adapters rather than implied behavior of these local APIs.

Canonical-path byte-boundary tests always exercise malformed UTF-8 refusal and valid U+FFFD/NFC/NFD preservation. A separate test constructs a raw invalid-UTF8 symlink target when the execution environment permits such filenames. The current local run cannot create that fixture: the sandbox returns `EPERM`, and a separate unsandboxed probe on the same volume returns `EILSEQ`. That end-to-end test is explicitly skipped here; the wrong-file selection scenario is not claimed as exercised on this host.
