# Pinned Java 21 floating-point conversion

`JavaFloatingPoint` calculates Java 21 `Float.toString` / `Double.toString`
selection and spelling directly from IEEE 754 binary32/binary64 bits. Its package
`decimalString` and `render` overloads have the same output. Numeric conversion
parses that spelling as an exact decimal and strips trailing zeros in the numeric
core; rendering retains the Java spelling. The numeric core rejects nonfinite
values before making operands. The converter itself can render `NaN`, `Infinity`,
and `-Infinity`, and preserves the sign of zero as `-0.0`.

Float is converted at its original binary32 width. Widening Float `0.1` to Double
before decimal selection would incorrectly turn `0.1` into
`0.10000000149011612`. Swift floating-point descriptions, Foundation number
formatters, locale data, and the host's floating-point printing algorithm never
participate in selection or formatting. Decimal integer digit extraction uses the
standard library's exact integer conversion.

## Algorithm and bounds

This is an original exact-integer rounding-interval search implementing the
[Java 21 Double decimal-selection contract](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Double.html#toString(double))
and the corresponding
[Float contract](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Float.html#toString(float)).
It is not a translation of the OpenJDK Schubfach implementation.

For a positive finite value `c * 2^q`, the lower and upper rounding boundaries are
`(4c - 2) * 2^(q - 2)` and `(4c + 2) * 2^(q - 2)`. At a normal power of two,
the preceding interval has half the following spacing, so the lower coefficient
is `4c - 1`; the normal/subnormal transition retains regular spacing. Boundaries
are included exactly when the binary significand is even. This also correctly
excludes the upper overflow boundary for the largest finite value.

The implementation estimates the decimal decade with integer arithmetic, then
corrects it with exact comparisons. It searches successively for decimals with
at most 2 through 9 (Float) or 17 (Double) significant digits, checks both adjacent
integer candidates on the relevant decimal grids against the exact interval,
and selects the closest by exact integer distance. Equal distances choose an
even normalized decimal significand. Starting at two implements Java's special
rule: if a one-digit decimal round-trips, decimals with either one or two digits
compete for the closest result. This makes the smallest positive Double
`4.9E-324`, rather than `5.0E-324`.

All arithmetic is private, unsigned, and bounded. Binary64 inputs need only
small finite exponents; decimal powers are generated by integer squaring, not
stored oracle answers. The quotient is at most 18 decimal digits and fits
UInt64. Intermediate storage has an explicit 68-word / 2,176-bit ceiling.
Selection must succeed within the IEEE 9/17-digit round-trip bounds. There are
no general-purpose arbitrary-precision dependencies or public big-integer APIs.

Formatting uses plain notation for decimal scientific exponents `-3...6`,
scientific notation otherwise, uppercase `E`, no positive exponent `+`, and at
least one digit after a decimal point. NaN payloads/signs canonicalize to `NaN`.
Finite signed values preserve their sign, including signed zero.

## Development oracle and archived evidence

The explicit local oracle is Amazon Corretto **21.0.11.10.1**, vendor
`Amazon.com Inc.`. The tool verifies the JDK `release` byte digest, the executable
version/vendor/build output, and all five corresponding source byte digests
before invoking Java. The Java oracle also validates its runtime version/vendor.
It consumes only width and raw bits, and returns Java's actual toString results;
it does not consume expected outputs or the behavioral corpus. It is development
code and never a package, consumer-build, or runtime dependency.

The cached OpenJDK implementation sources were reviewed as reference and pinned
for oracle provenance. They carry GPL v2 with the Classpath exception. No source,
lookup tables, or translated implementation from those files is incorporated
into this Apache-licensed Swift code. The mathematical powers used at runtime
are calculated from 10; test-only expected decimals are obtained by running the
pinned Java API.

`Reference/floating-point-goldens.json` archives **1,592** actual oracle outputs
(782 Float and 810 Double), including raw bits and oracle provenance. It is a
separate development artifact, outside the immutable common-corpus baseline.
The Python tool pins its whole-file SHA and independently reconstructs its exact
bit inventory. Its normal `--check` compiles the production Swift converter in
an isolated temporary directory, checks both conversion/rendering overloads
against these goldens, and needs only Python's standard library and `swiftc`.
No sibling repository, JDK, Node, network, or generated expected-value table is
needed. Native XCTest also checks the goldens and finite bit-exact round trips.

Run from the package root:

```sh
python3 Tools/verify_floating_point.py --check
python3 Tools/verify_floating_point.py --oracle \
  --jdk /path/to/amazon-corretto-21.jdk/Contents/Home \
  --report /tmp/lokalized-floating-oracle-report.json
```

The default broad oracle uses a fixed xorshift64 seed `8d351a69c27f045b`, 32,768
independent raw-bit random inputs per width, every binary exponent boundary and
adjacent significands, decimal-power neighbors, normal/subnormal boundaries,
first 2,048 Float and first 256 Double subnormals, both signs, signed zeros,
infinities, multiple NaN signs/payloads, and exact closest-decimal midpoint ties.
An explicit `--refresh-goldens --jdk ...` regenerates the small archive only
after actual Swift/Java agreement; deliberate refresh also requires updating
its fixed SHA pin. No oracle is automatically found or fetched.

## M2 validation and measured tradeoff

On 2026-10-01 the default broad probe passed **103,310** inputs with **zero
differences**: 40,644 Float and 62,666 Double. The report is reproducible from the
command above and records source/toolchain digests, input/output digests, counts,
and timing. The production source used for this run had SHA256
`e866ebbab3c9d7dc43c9cbd9287521cb1ce0a7228b61e7a9d4e17084edd129c3`.
The input SHA256 was
`d2e76abccf07be0ada604c3a1d4977b7be4f28cbee509cb28b785d3e706cc170`;
the output SHA256 was
`e4aa9b377b90f1b75fd1b241e590d21da5357e0530f784c0680111cf743b6686`.
The local evidence file was
`/private/tmp/lokalized-m2-floating-oracle-report.json` (a development report,
not a required checkout file).

The measured platform was arm64 macOS 27.0.1, Apple Swift 6.4
(`swiftlang-6.4.0.34.1`), compiling with `-O` and Swift 6 language mode. The
application driver compile took 0.946 seconds with the installed system SDK;
this does not measure a cold SDK/module cache or the declared minimum Swift 6.2
toolchain. Native tests in an isolated package passed all four methods with
zero failures; its 1,592-golden/round-trip method took 8.415 seconds in debug.
The real package filter subsequently passed all four tests too (golden method
8.634 seconds). The same normal Python golden check passed 1,592 inputs,
including a copied tool/source/golden tree with no sibling repositories or JDK.
Negative checks rejected a changed expected decimal and an unpinned JDK release
before Java execution.

The broad Swift driver took **23.177 seconds**, about **224 microseconds per
mixed input**, while the Java oracle driver took **0.179 seconds**. Both include
line input/output; the Swift driver requests `decimalString` and `render` and
checks their equality for each input, while Java requests one toString. These
are driver timings, not isolated per-conversion microbenchmarks. The original
bounded algorithm favors auditable correctness and license clarity over
Schubfach throughput; it allocates small temporary word arrays. This is a known
M2 performance tradeoff. Future optimization must preserve the same exact
selection and run both the broad oracle and the native goldens. This evidence
is not an exhaustive enumeration of all binary patterns, minimum-OS execution,
or a minimum-toolchain qualification.
